# Homebridge 기능 확장 액션 체크리스트

작성일: 2026-09-30

상태: 3.0.0-beta.1 출시 후보. 2.1.0-beta.1에서 수행한 기능 구현·검증 결과를 이어받고 버전과 사용자 문서를 갱신했다. 체크한 작업만 완료이며, 실기·공급자 계약·호스트 알파 제한이 남은 항목은 열린 상태로 유지한다.

대상: `@chazepps/homebridge-hejhome`, `codex/hejhome-2.1.0-beta`

기준 구현: `edbf64a` / `2.1.0-beta.0`

근거: [기능 차이 조사](../references/homebridge-feature-gaps-2026-09-30.md), [기존 베타 실행 기록](2026-09-30-2.1.0-beta.md), [베타 사용·출시 안내](../product-specs/3.0-beta-guide.md)

진행 결과: [기능 구현 및 검증 기록](2026-09-30-feature-implementation-status.md). 체크는 항목 단위의 완료이며 기능 전체의 실기 인수를 의미하지 않는다.

**집계 원칙:** 아래 체크박스는 원본 **155개**를 유지한다. 복합 항목은 어느 한 조건이라도 남으면 `[ ]`로 두고, 바로 아래의 `코드·로컬 검증 / 실기·공급자 계약 / 호스트·게시` 메모로 분리한다. 메모는 새 완료 항목으로 세지 않는다. `3.0.0-beta.1`은 로컬 후보이며 Node 22.12 clean-install 실패로 지원 하한을 **22.13**으로 정정했다. 이전 소스 테스트·패키지는 이력으로 보존하고, 새 SHA 패키지의 Node×Homebridge 6셀·격리 복귀는 통과했다. 분리된 UI fixture를 포함한 최종 verify·실기·게시 후 확인은 별도 게이트다.

## 0. 실행 원칙과 완료 기록

- [x] 착수 시 현재 브랜치·커밋·변경 파일과 npm의 Homebridge/UI 정식·베타·알파 버전을 다시 확인한다. 조사 당시 버전을 최신이라고 고정하지 않는다.
- [x] 기존 구현인 Matter 기본 노출, 모델별 계측 변환, LightWw Adaptive Lighting, 상태 공유, 캐시 복원, 베타 게시 정책, Node 22/24/26 검증은 회귀 기준으로 유지한다.
- [x] 각 항목의 지원 모델·프로토콜·읽기/쓰기 범위를 먼저 명시한다. Homebridge API 존재와 Hejhome 실물 지원을 구분한다.
- [ ] 실제 데이터가 필요한 항목은 비식별화한 필드·값·단위·순서·실패 응답을 fixture로 남긴다. 비밀번호·토큰·쿠키·원본 계정정보는 문서나 fixture에 넣지 않는다.
- [x] 동작 변경마다 기대 행동을 검증하는 실패 테스트를 먼저 만들고, 구현 후 통과 결과를 기록한다.
- [x] 각 단계 종료 시 코드·문서·fixture 또는 검증 로그를 산출한다. 실기 성공은 명령 송신, 실제 장치 동작, 상태 재수신을 함께 확인한다.
- [x] 실패하면 원인, 이전 시도가 실패한 이유, 다른 접근을 기록하고 해당 단계만 재시도한다.
- [x] 기능을 완료 표시할 때 아래 기록 양식을 채운다. 코드 완료·로컬 검증·실기 검증·배포 상태는 각각 기록한다.
- [x] 현재 작업은 준비 범위로 유지한다. npm 게시, 릴리스 태그 push, 운영 Homebridge 설치·업데이트는 별도 명시 지시 전에는 실행하지 않는다.

## 1. 권장 진행 순서

1. B1·B2·B3의 실제 장치 데이터 수집과 지원 표기 정정부터 시작한다.
2. A1·A2의 상태 신뢰성·복구와 A4 진단 화면을 구현한다. B1–B3의 검증된 매핑을 연결한다.
3. A3·A5·A6, B4·B5·B6·B7을 모델별로 진행하고 A7 UI 품질을 보완한다.
4. C0 환경에서 C1–C5 Smart Automation 호환성을 검증한다. 센서 신뢰성 검증을 먼저 마친다.
5. B8·B9·B10은 장비 계약과 규모에 따라 별도 구현 단위로 진행한다. 카메라와 HKSV를 한 번에 완료 처리하지 않는다.
6. D의 범위 점검과 R의 베타 출시 게이트를 통과한 항목만 릴리스 범위에 넣는다.

## A. 기존 연동 수단으로 착수 가능한 7개 항목

### A1. 연결 상태·데이터 신선도·오류 표현 — P1

대상: `src/platform.ts`, `src/platformAccessory.ts`, `src/matter/`, `src/hej/realtime.ts`.

- [x] REST 인증 상태, MQTT 연결 상태, 장치 온라인 상태, 개별 측정값의 마지막 수신 시각을 별도 관리한다.
- [x] 센서별 보고 주기를 고려한 만료 정책을 정하고, 이벤트형 센서를 단순 무수신만으로 오프라인 판정하지 않도록 테스트한다.
  - 코드·로컬 검증: 환경 측정 90분, 계측 5분, 장치별 선택 만료와 이벤트 무기한 정책 및 결측·시간 역행 테스트 완료. 실제 모델별 주기와 컨트롤러 표시는 아래 실기 항목에 남음.
- [x] 알 수 없거나 만료된 상태를 온도 0, 배터리 100%, 누수 없음 등 정상값으로 대체하지 않는다.
- [x] 지원되는 HAP 서비스에 `StatusActive`/`StatusFault`를 적용하고 필요한 읽기에는 통신 오류를 반환한다. Matter는 `reachable`과 nullable 측정값을 적절히 갱신한다.
- [x] REST 401 중 MQTT 정상, MQTT 단절, 장치 단독 오프라인, 일부 센서값만 만료, 재연결 후 정상 복귀를 테스트한다.
- [ ] 실기에서 컨트롤러의 표시와 복구 시각을 확인한다.

완료 조건: 서로 다른 장애 원인이 분리 표시되고, 오래된 값이 정상 최신값으로 오인되지 않으며 실제 데이터 수신 후 복귀한다.

### A2. 재시작 없는 세션 복구·재탐색 — P1

대상: `src/platform.ts`, `src/storage/sessionStore.ts`, `src/hej/`, `homebridge-ui/server.js`. 의존: A1의 상태 정의.

- [x] UI 재로그인으로 세션 파일이 교체될 때 이를 감지하는 경로를 추가한다.
- [x] 기존 REST/MQTT 클라이언트를 안전하게 정리하고 새 세션으로 교체한다. 중복 연결·구독·watcher를 방지한다.
- [x] MQTT 재연결 이후 전체 상태 재조회와 선택한 집·방의 장치 재탐색을 수행한다. 재시도 간격과 요청량 상한을 둔다.
- [x] 일부 집 조회 실패 시 캐시 장치를 삭제하지 않는다. 전체 성공 결과에서만 추가·변경·제거를 반영한다.

- [x] 공급자 토큰 갱신 절차가 입증되지 않으면 자동 갱신을 약속하지 않고 재로그인 안내로 연결한다.
- [ ] 실기에서 프로세스 재시작 없이 재로그인과 상태 복구가 끝나는지 확인한다.

완료 조건: 정상 세션 교체·재연결·장치 변경이 재시작 없이 반영되고 실패한 조회가 기존 장치 제거로 이어지지 않는다.

### A3. Matter 상대 밝기·연속 조절 — P2

대상: `src/matter/accessory.ts`, 조명 제어 큐. 상대 조절과 연속 조절을 별도 완료 처리한다.

- [x] 현재 밝기가 불명확할 때의 조회 또는 오류 정책을 정한다. 실패한 명령을 성공으로 보고하지 않는다.
- [ ] 반복 상대 조절, 양 끝값, HAP/Matter 동시 조작, 실패 후 상태 복귀를 테스트하고 실기 확인한다.

완료 조건: 상대 조절이 기존 절대 제어와 일관되게 작동한다. 연속 조절은 정지·시간 상한·요청 예산까지 통과했을 때만 지원으로 표시한다.

### A4. 실시간 HAP/Matter 진단 화면 — P1

대상: `homebridge-ui/`, 상태·로그 저장 모듈. 의존: A1·A2.

- [x] Hejhome 발견 상태, HAP 등록 상태, Matter 등록 상태를 장치별로 구분하는 읽기 전용 진단 모델을 만든다.
- [x] `getCachedAccessories`, `getCachedMatterAccessories`를 사용하되 캐시 존재를 현재 연결·페어링 성공으로 표시하지 않는다.
- [x] 마지막 센서 수신, 마지막 명령 결과, 세션 상태, MQTT 상태, 계측 프로필 적용 여부를 표시한다.
- [x] `pushEvent`와 UI 이벤트 구독을 연결하고 화면 닫힘·재열림 시 구독과 자원을 정리한다.
- [x] 비식별 진단 내보내기를 제공하고 토큰·쿠키·계정정보가 포함되지 않는지 검증한다.
- [ ] 부분 장애·미페어링·오래된 캐시·재연결 상황을 UI 테스트와 실기에서 확인한다.
  - 코드·UI 검증: 캐시/등록/연결 분리 및 재연결 화면 테스트 완료. 실기: 실제 페어링·부분 장애 표시 대기.

완료 조건: 사용자가 어느 단계에서 장치가 멈췄는지 구분하고, 화면 새로고침 없이 상태 변화를 볼 수 있다.

### B9. 카메라 미리보기·영상·HKSV — P3 / 별도 대형 작업

- [ ] 반대 명령 경합·응답 없음·상태 불명·물리 조작·재시작을 테스트한다.
- [ ] 실제 상태 재수신까지 확인한 모델만 제어 지원으로 표시한다.

완료 조건: 읽기/쓰기 지원 범위가 명확하고 실제 장치 상태와 컨트롤러 표시가 일치한다.

## D. 호스트 기능·추가 범위 점검

- [x] 일괄 업데이트, IPv6/mDNS 설정, 브리지 페어링 UI는 호스트 기능으로 분류하고 플러그인에는 호환성 검증·안내만 추가한다.
- [ ] Matter multi-admin과 HAP/Matter 공존은 호스트에서 제공되는 범위와 실제 페어링 결과를 확인하고 A4·A5의 진단·장치 선택과 연결한다.
- [x] Thread 무선 기능, Hejhome 로컬 제어, 공급자 펌웨어 업데이트를 Matter 추가만으로 제공한다고 표시하지 않는다. 추진 시 별도 하드웨어/API 근거를 요구한다.
- [x] 이력 차트 또는 Eve 전용 history를 추진하려면 저장 기간·용량·데이터 삭제·호환 프로토콜·라이브러리 유지보수를 별도 설계한다. 기본 Homebridge 기능으로 간주하지 않는다. [설계 조건](../design-docs/device-history.md)만 완료했고 이력 기능은 구현하지 않았다.
- [x] 로봇청소기·밸브·펌프 등 현재 registry에 없는 제품군은 실제 Hejhome 모델·API가 확인될 때만 새 지원 항목으로 등록한다.
- [x] 모델·펌웨어 정보를 실제 제공받는 경우에만 HAP/Matter 메타데이터에 반영한다. 확인하지 않은 값을 제조사 사실처럼 표시하지 않는다.

완료 조건: 플러그인 구현, 호스트가 제공하는 기능, 추가 조사 과제가 지원 문서에서 구분된다.
