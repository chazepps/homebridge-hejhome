# Homebridge 기능 확장 구현·검증 기록

작성일: 2026-09-30. 현재 대상: `codex/hejhome-2.1.0-beta`, `3.0.0-beta.1` 로컬 후보. 아래 기능 구현과 실기 범위는 `2.1.0-beta.1`에서 시작한 검증 이력을 포함한다.

[전체 액션 체크리스트](2026-09-30-homebridge-feature-action-checklist.md)의 완료 표시는 이 기록을 근거로 한다. 155개 항목을 모두 완료한 것으로 표시하지 않는다. 코드를 구현한 범위, 코드로 검증한 범위, 실제 기기 계약이 없어 구현하지 않은 범위를 구분한다.

**이번 추가 작업의 집계:** 체크리스트의 원본 155개 항목은 유지했다. 한 문장에 코드·로컬 테스트와 실기 확인이 함께 들어 있으면 전자가 통과해도 원 항목은 열어 두고 세부 상태를 별도로 기록한다. 이 절 아래의 이전 3.0.0-beta.1 패키지 수치와 SHA-256은 **대체된 로컬 후보**의 이력이다. Node 22.12 clean-install 실패에 따라 지원 하한을 22.13으로 수정했고 새 package/lock/CI/가이드를 반영한 tarball의 내용·해시·6셀·격리 복귀와 분리한 fixture를 포함한 최종 verify를 확인했다. 로컬 준비와 실제 실기·게시를 구분한다.

### 최종 verify의 테스트 fixture 수정

`/tmp/hej-3-completion-verify.log`의 최종 `npm run verify`는 PASS다. 그 전의 두 실패는 production 결함이 아니었다. UI 테스트는 로그 I/O와 19개 직렬 시나리오를 한 테스트의 5초 제한에 넣어 고부하에서 timeout이 났다. 초기 상태가 독립인 세 테스트로 나누고 `LogStore`를 테스트 경계에서 대체해 재실행했다. runtime lifecycle 테스트는 teardown에서 shutdown Promise를 버리고 40ms 뒤 임시 디렉터리를 지워 `RuntimeStatusStore.flush`와 경합했다. shutdown Promise와 실제 flush를 기다리고 비대상 `LogStore`를 테스트에서 대체했다. 생산 코드와 위 tarball 내용은 변하지 않았고, 수정된 fixture를 포함한 전체 403개 코드·29개 UI 테스트가 통과했다. 실패한 시도와 원인·다른 접근을 보존하되 최종 PASS만 출시 게이트에 사용한다.

### Node 22.12 clean-install 실패와 재시도

Node 22.12.0에서 기존 400개 소스 테스트는 Node 24에서 설치한 의존성을 재사용해 통과했다. 이는 깨끗한 설치 증거가 아니었다. 이전 tarball의 격리 매트릭스에서는 `@matter/nodejs@0.17.9`의 `engines`가 `>=20.19 <22 || >=22.13`인 데 비해 선언 하한이 22.12여서 optional package가 설치되지 않았고 native import가 실패했다. 원인은 소스 테스트가 아니라 **지원 하한과 의존성 계약의 불일치**다. 이전 패키지와 로그는 실패 원인 추적으로 보존하고, package/lock/CI/사용자 문서를 22.13으로 맞춘 새 tarball SHA `f44a1fada4f61e86a1d79ce1a2e516c80d8a2970caa1c1fee1c7254c74af9b04`로 6셀을 다시 실행해 모두 통과했다. 같은 버전 번호라도 해시가 다른 후보를 혼합해 성공으로 집계하지 않는다.

### 새 패키지 격리 매트릭스와 복귀

`/tmp/hej-matrix-3beta1-node2213-final/summary.json`에서 SHA `f44a1fada4f61e86a1d79ce1a2e516c80d8a2970caa1c1fee1c7254c74af9b04`를 root가 직접 확인했다. Node **22.13.0 / 24.4.1 / 26.10.0** × Homebridge **2.4.0 / 2.4.1-beta.11** 여섯 셀이 모두 통과했다. 각 셀은 설치된 패키지만 사용해 14개 장치 계열을 세 개의 별도 Node 프로세스로 등록·재시작·복원하고, 숨김·재등록·PM child 결함 복구와 `null→15` 농도 갱신·전체 Matter opt-out을 검사했다. fake sender에 기록된 vendorCommands=1은 스모크의 합성 명령이며 실제 공급자 명령은 **0건**이다. registry의 `latest=2.1.1`을 고정해 격리 설치 `2.1.1→3.0.0-beta.1→2.1.1` 복귀도 통과했다. Matter controller commissioning이나 운영 설치·실기 rollback 증거로 확대하지 않는다.

## 3.0.0-beta.1 문서·버전 정리 (추가 기능 착수 전 기록)

사용자 요청에 따라 로컬 후보 버전을 `3.0.0-beta.1`로 변경했다. README에 지원 범위, 2.x에서 달라지는 환경·서비스, 설치 시점, 정식 버전 복귀 절차를 정리했다. package/lockfile, 설정 화면의 한영 제목, 당시 가이드와 링크도 맞췄다. 이 문서 정리만으로 장치 제어 동작과 미완료 항목이 변경된 것은 아니며, 이후의 B6/B8/B10 추가 구현은 위 표에서 별도로 추적한다.

- 릴리스 채널 검사는 `beta`를 반환한다. 정식 `latest`와 분리하는 정책을 유지한다.
- lint/typecheck/build 통과 후 문서·버전 테스트에서 실패한 3건을 조사했다. 이전 README 문장 단정, Git에 아직 반영되지 않은 문서 이동, 일괄 치환으로 의미가 바뀐 잘못된 버전 예제가 원인이었다. 새 안내에 맞춘 단정·문서 이동 반영·leading-zero 예제 복원 후 집중 테스트 10개, 전체 코드 테스트 287개, 화면 테스트 26개가 통과했다. 수정한 테스트의 lint와 문서 검사도 통과했다.
- `npm pack --dry-run`과 실제 tarball 검사를 통과했다. 패키지의 버전·`beta` 채널·README·설정 화면·새 가이드·컴파일 결과를 확인했다.
- 패키지: `chazepps-homebridge-hejhome-3.0.0-beta.1.tgz`, 101개 파일, 756,473 bytes.
- SHA-256: `0d4685a042c707150eab2b2820b00f7caa1eabe84c7b268897226d7c03fb73e2`.
- 이번 3.0 후보는 게시하지 않았다. 운영 설치, 원격 설정 변경, 태그 push도 수행하지 않았다. 아래 Node 22/26·베타 호스트 실험 기록은 별도로 재실행했다고 주장하지 않고 당시 버전의 증거로 보존한다.

## 실행 환경과 작업 경계

- 사용자 요청에 따라 7개 서브에이전트가 서로 다른 파일 영역을 병렬 구현했고, 비작성자가 영역별 독립 리뷰를 수행했다.
- `czmm`에서 저장된 Homebridge 장비 목록과 설치 버전만 읽었다. 기기를 조작하거나 서비스·플러그인을 설치/재시작하지 않았다.
- 확인된 설치 버전: core 2.4.1-beta.11, UI 6.0.1-alpha.20, Hejhome 2.0.2.
- 저장된 장비 목록에는 릴레이 1개, RGBW 조명 1개, 벽 스위치 4개, 모션 센서 1개가 있다. 장치 이름·식별자·계정 없이 종류와 필드만 `tests/fixtures/czmm-capability-inventory-20260930.json`에 남겼다.
- 공개 공급자 웹 코드의 필드·단위 변환·명령 순서를 조사했다. 원본 UI 코드나 비밀을 배포 문서에 복사하지 않았다.
- `latest`/`beta` dist-tag, 운영 설치, 원격 설정을 변경하지 않았다.

## 중요한 구현 경계

### 공유 상태와 명령

`src/runtime/`는 상태·측정 신선도·필드별 관측 버전·진단 저장·로컬 명령 전달을 분리한다. `src/platform.ts`의 장치 저장소는 HAP 노출과 독립적이다. UI 리모컨도 같은 장치별 명령 대기열을 사용한다. 느린 응답보다 새 MQTT 관측이 우선이며, HAP/Matter 프레임워크의 쓰기 완료 이후에도 최신 상태를 유지하도록 검증했다.

UI 명령 전달은 해당 저장 공간의 제한된 Unix socket을 사용한다. 요청 크기·유효시간·동일 요청 재전송을 제한하고 다른 프로세스의 활성 socket을 삭제하지 않는다. 종료는 대기 명령을 취소하며 자동 재전송하지 않는다. Windows의 새 UI 리모컨 경로와 너무 긴 socket 경로는 준비 불가로 표시한다. 기존 HAP/Matter 경로와 분리된 제한이다.

### 검증되지 않은 상태를 만들지 않기

현재 온도와 설정 온도, 릴레이 전원과 실제 부하, 명령 전송과 물리 동작을 구분한다. 미등록 기기를 임의 relay로 만들지 않는다. ID 없는 캐시는 추측해 삭제하지 않는다. 피드백 없는 IR은 순간 버튼으로 처리하며, Matter 절대 전원 장치로 가장하지 않는다.

에어컨의 공통 웹 명령은 확인됐지만 필수 실제 운전 상태가 없다. 항상 오류를 내는 온도조절기 서비스를 노출하는 대신 확인된 전원과 설정 화면 조작을 제공한다. 기존 자동화가 해당 서비스에 연결되어 있다면 사용자 안내에 따라 변경 영향을 확인해야 한다.

### 자동화는 호스트 알파의 한계까지 기록

공식 UI 태그 `v6.0.1-alpha.20`, commit `b85d97ff3777c6f72a451db9ba8c16bd530fab42` 기준이다. 규칙을 복제하지 않고 그 소스를 별도 환경에서 실행했다.

- C1: 개별 조명 변경의 그룹 표시 역반영이 없다.
- C2/C3: 마지막 센서값의 나이·오류 상태를 규칙 자체가 검사하지 않는다.
- C4: 모든 입력 읽기가 실패해도 가상 센서가 마지막 평균값을 유지한다.
- C5: 입력 센서를 찾지 못해도 경계를 허용할 수 있다.

이 결과를 안전 호환성 통과로 표시하지 않는다. [고객 가이드](../product-specs/smart-automation-guide.md)에 각 제한과 확인 방법을 기록했다.

## 리뷰와 수정 근거

각 구현자와 다른 작업자가 runtime, HAP, Matter, UI/config, IPC를 검토했다. 중요한 결함은 재현 테스트를 추가한 뒤 수정했고, 원인과 수정 결과를 작업 보고에 남겼다. 대표 사례는 다음과 같다.

- 세션 교체 후 이전 장치 접근, 실패한 재탐색 삭제, reconnect 중 놓친 변경 복구.
- 헤더 수신 후 응답 본문 무한 대기와 세션 교체 시 HTTP 취소.
- 느린 REST 응답이 최신 MQTT 값을 덮는 문제 및 서로 무관한 필드 충돌 구분.
- Adaptive Lighting 제거가 저장 예약을 지우는 문제와 실제 ControllerStorage 복원.
- 실제 HAP 순간 버튼이 완료 뒤 켜짐으로 되돌아가는 문제.
- 연속 조광 재시작으로 요청 예산을 우회하거나 지연된 자체 보고를 사용자 조작으로 오인하는 문제.
- 만료된 부하 상태가 애매한 새 측정으로 정상 상태처럼 되살아나는 문제.
- 실시간 진단 갱신이 입력 중 설정을 지우는 문제, 원본 계측 편집/삭제 무시, 과거 기록의 제어 버튼 활성화.
- 서로 다른 설정 저장 경로의 검증 우회, 등록 준비와 실제 앱 연결의 문구 혼동.
- 밝은 테마 배지 대비 부족: 브라우저 계산 기준 4.5:1 이상으로 보완.

## 남은 작업을 끝내는 데 필요한 근거

버튼 gesture, 팬 단계·회전 상태, 레이더 지속 재실, 커튼 정지·각도, PM2.5 실제 단위/모델 배율, 카메라 스트림, 잠금/경보 제어는 해당 모델의 비식별 실제 보고/명령 응답과 물리 동작 의미가 필요하다. 반면 공개 코드로 확인된 비-IR 공기청정기 전원·모드와 도어락 문 열림은 모델·필드 범위를 좁혀 추가 구현한다. 현재 등록된 7개 장비로 얻을 수 없는 데이터를 추정하지 않는다. 카메라 영상과 잠금/경보 제어는 불완전한 틀만 추가해 구현 완료로 표시하지 않았다.

코드로 검증 가능한 공통 기능은 구현했으나, 열린 체크박스는 아직 해결되지 않은 실제 조건이다. 별도 장비나 공급자 계약이 확보되면 같은 ID의 항목에서 이어서 진행한다.

## 열린 조건의 종류

아래 범주는 서로 겹치므로 합산해 체크박스 개수로 사용하지 않는다. 숫자 집계는 원본 155개 체크리스트만 기준으로 한다.

| 종류 | 열린 항목과 필요한 증거 |
| --- | --- |
| 공급자 장치 계약 | B1은 버튼 번호·제스처 enum·중복 식별, B2는 선풍기 단계/회전 상태, B3은 모델별 냉난방 능력·실제 운전 상태, B4는 지속 점유·부재 지연, B5는 stop/tilt·각도 단위, B6은 실제 PM2.5 단위·배율/필터, B7은 RGBW 색온도·장면·XY, B8은 입력/방향·재생, B9는 영상/스냅샷/녹화 codec·세션, B10은 잠금·사이렌 상태·명령이 필요하다. |
